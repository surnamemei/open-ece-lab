# OpenECE Lab

OpenECE Lab is a hardware-agnostic measurement, analysis and validation tool for electronics,
control and signal-processing work. It takes measured (or simulated) data, runs an engineering
analysis, checks the results against a specification, and writes a traceable **run record**
(JSON) plus a self-contained **HTML report** for every run:

`input file or instrument -> import -> analysis -> PASS/FAIL -> record + report`

The same analysis code serves data files and instrument backends. Today the instrument backends
are **mock (simulated) instruments**. Real instruments are a later gate and must plug in behind
the same interfaces.

## v0.1 scope

| Area | What v0.1 does |
| --- | --- |
| File import | CSV/TSV/TXT (delimiter, header, units row, comments, decimal comma, ISO timestamps), WAV (PCM 8/16/24/32-bit and float, mono/stereo/multichannel), NPY |
| Column mapping | recognised names (`time`, `timestamp`, `t`, `frequency`, `magnitude`, `phase`, ...), explicit mapping, **errors instead of guesses** when ambiguous |
| Units | read from headers (`time (ms)`, `gain [dB]`, `frequency_hz`), converted explicitly, reported with every result |
| Analyses | Bode / -3 dB cutoff, step response (rise, overshoot, settling, steady-state error), signal (levels, dominant frequency, FFT, Welch PSD) |
| Validation | inclusive min/max limits from a YAML spec or `--require NAME=MIN:MAX`, PASS/FAIL per check |
| Records | one folder per run with `record.json` (ID, timestamp, source + SHA-256, parameters, results with units, validation, artifacts, software version); never overwritten |
| Reports | self-contained HTML with figures; simulated data is labelled as such |
| Entry point | `open-ece` command-line tool (`python -m openece` also works) |
| Mock instruments | signal generator, oscilloscope and power supply; recipe-driven RC sweep demo |

**Physical instrument support is not required for v0.1.** Everything above runs on files and
mock instruments. No vendor SDK (for example Analog Discovery) is a dependency.

## Installation

Requires Python 3.11 or newer on Windows or Linux (macOS should work but is not tested in CI).

```bash
git clone <your repository URL> open-ece-lab
cd open-ece-lab
python -m venv .venv
```

Activate the environment. On Linux or macOS:

```bash
source .venv/bin/activate
```

On Windows (PowerShell): `.venv\Scripts\Activate.ps1`. Then install the package with its
development extras:

```bash
pip install -e ".[dev]"
```

The dependencies are numpy, scipy, matplotlib and PyYAML, plus pytest for development.

## Example commands

Analyse the example datasets. Each command also works without `--spec`, in which case the result
is reported as `NOT EVALUATED`.

```bash
open-ece analyze-step examples/motor_step.csv --spec examples/specs/motor_step.yaml
```

```bash
open-ece analyze-signal examples/signal.wav --spec examples/specs/signal_1khz.yaml
```

Add or override a limit on the command line. The limit below makes this run FAIL, with exit
code 1:

```bash
open-ece analyze-step examples/motor_step.csv --reference 1000 --require overshoot_percent=:5
```

See how a file will be imported (columns, units, recognised roles) before analysing it:

```bash
open-ece inspect examples/rc_sweep.csv
```

Map columns explicitly, for example when a log has both a command and a speed column:

```bash
open-ece analyze-step mylog.csv --time-column "t (ms)" --response-column speed
```

Choose a channel of a stereo WAV file (channels are named `ch1`, `ch2`, ...):

```bash
open-ece analyze-signal capture.wav --channel ch2
```

Import a European CSV (`Frequenz (Hz);Betrag (dB)` with values such as `1591,5;-3,0`). It uses a
semicolon delimiter, a decimal comma and header names that are not recognised automatically:

```bash
open-ece analyze-bode messung.csv --decimal , --frequency-column Frequenz --magnitude-column Betrag
```

List stored runs, and print one record by ID or a unique prefix of the ID:

```bash
open-ece runs list
```

```bash
open-ece runs show 20260926T075857Z
```

Run the Gate 0 mock-instrument demo. Its report and record are clearly labelled SIMULATED:

```bash
open-ece demo-rc --recipe examples/recipes/rc_lowpass.yaml
```

`open-ece --help` and `open-ece <command> --help` list every option. `openece` (the Gate 0
command name) is kept as an alias.

**Exit codes:** `0` = completed (PASS, or no requirements), `1` = completed with FAIL,
`2` = input/usage error (with a message and a hint), `3` = unexpected internal error.

## How input files are read

- **CSV/TSV/TXT:** `#` comment lines are kept as provenance; the delimiter (`,` `;` tab or
  whitespace) is detected; the first row is the header unless it is all numeric. A row of units
  under the header (PicoScope style) is recognised. A column is numeric only if every non-blank
  cell parses; otherwise it is reported with the first bad line and never silently converted.
  ISO 8601 date-times are converted to seconds since the first sample. Decimal commas need
  `--decimal ,`; metadata preambles need `--skip-rows N` or `#` prefixes.
- **WAV:** the sample rate, channel layout, encoding, bit depth and any RIFF `INFO` comment are
  recorded. Samples are scaled to **FS** (fraction of digital full scale); WAV carries no
  physical units, so nothing is labelled as volts. Multichannel files are never mixed down; you
  choose a channel.
- **NPY:** 1-D, 2-D (samples x columns) or structured arrays; pickled/object arrays are refused.
- **Column roles** are filled by an explicit option first, then by a recognised name, then (for
  the main data column only) by being the single remaining numeric column. Anything else is an
  error that lists the candidates and the option to use.
- **Units** come from headers: `name (unit)`, `name [unit]` or suffixes such as `_s`, `_ms`,
  `_hz`, `_db`, `_deg`. Time defaults to seconds and frequency to Hz, each with a visible
  warning. Magnitude (dB or linear) and phase (deg or rad) are **never assumed**. Use
  `--magnitude-unit` or `--phase-unit` when a header has no unit.

## Run records

Each run folder contains `record.json`, `report.html`, figures (`*.png`) and data tables
(`*.csv`). Folders are created exclusively, and files are never replaced, so earlier runs can't
be overwritten. The record, schema `openece.run-record` version 1, contains:

| Key | Content |
| --- | --- |
| `run_id`, `created_utc`, `status` | unique, sortable ID (`YYYYMMDDTHHMMSSZ-<analysis>-<random>`), ISO 8601 UTC time |
| `analysis` | type, title and every effective parameter, including how each column was chosen and unit conversions |
| `source` | file path, absolute path, format, size, **SHA-256** and import metadata (delimiter, header line, comments, WAV encoding, ...); or the instrument backend with `"simulated": true` for mock instruments |
| `results` | `{name: {value, unit, description, note?}}`; values that can't be determined are `null` with a note |
| `validation` | `overall` (`PASS`/`FAIL`/`NOT_EVALUATED`), spec name/path/SHA-256, and each check with limits and detail |
| `artifacts` | files in the run folder (paths relative to it), with kind and description |
| `software` | OpenECE Lab version, Python, platform, dependency versions, git commit (and whether the package has uncommitted changes) when run from a checkout |
| `warnings`, `invocation` | everything the user was warned about; the command line and working directory |

The JSON is strict: no `NaN` or `Infinity`.

## Specs (requirements)

A spec is a small YAML file. Limits are inclusive and use each result's unit:

```yaml
name: Motor speed loop step acceptance
analysis: step              # optional; rejects use with another analysis
parameters:                 # optional default analysis parameters
  reference: 1000
requirements:
  overshoot_percent: {max: 15}
  settling_time_s: {max: 0.4}
  steady_state_error_percent: {min: -2, max: 2}
```

A requirement that names an unknown result is an error (it catches typos). A result that could
not be determined (for example no -3 dB crossing in the sweep) FAILs its requirement.

## Python API

The CLI is a thin layer over the same functions:

```python
from openece.io import load_file
from openece.records import RunStore
from openece.validation import Requirement
from openece.workflows import analyze_bode, apply_requirements, save_run

data = load_file("examples/rc_sweep.csv")          # Dataset: columns, units, provenance
outcome = analyze_bode(data)                         # typed results with units, no files written
outcome = apply_requirements(outcome, [Requirement("cutoff_hz", 1450, 1750)])
saved = save_run(outcome, RunStore("runs"))          # record.json + report.html + figures
print(outcome.results["cutoff_hz"].value, outcome.overall, saved.report_path)
```

## Repository architecture

```text
src/openece/
  analysis/      pure numerical algorithms (numpy/scipy only): signal, control, electronics
  io/            file import -> Dataset (CSV, WAV, NPY), column-role resolution
  units.py       unit parsing and explicit conversions
  instruments/   instrument interfaces (base.py) and mock backends (mock.py)
  measurements/  measurement procedures that drive instruments through the interfaces
  recipes/       YAML measurement recipes and specs
  validation.py  requirements and PASS/FAIL checks
  records.py     run records (JSON) and the append-only run store
  reporting/     presentation: HTML report and matplotlib figures
  workflows/     orchestration: import -> analysis -> validation -> record/report
  cli.py         command-line front-end (argument parsing and printing only)
  errors.py      user-facing error types
examples/        synthetic example data, specs and the mock recipe
scripts/         generate_examples.py (reproducible example data)
tests/           deterministic tests, including an import-boundary test for the layers
```

Dependencies point one way: `cli -> workflows -> {io, analysis, measurements, instruments,
validation, records, reporting}`. Analysis code never imports IO, instruments, reporting or UI
code. `tests/test_architecture.py` enforces these rules, and [AGENTS.md](AGENTS.md) describes
them for contributors and coding agents.

## Current limitations

- **No physical instruments yet.** Only mock backends exist; their data is always labelled as
  simulated. File data is recorded with its checksum and comments, but OpenECE Lab cannot verify
  whether a file came from a physical measurement.
- **Bode:** only the upper (low-pass) cutoff is estimated. It is defined at exactly 3.000 dB
  below the maximum magnitude, so a first-order RC reads 0.24 % below 1/(2πRC); use
  `--drop-db 3.0103` for the half-power point. The maximum sample is the reference level, so
  noise in the passband biases the cutoff slightly. High-pass/band-pass lower edges are not
  estimated. Magnitude/phase input only (no complex or Vin/Vout amplitude pairs).
- **Step:** positive-going steps only. Times are reported on the file's time axis unless
  `--step-time` is given.
- **Signal:** the dominant frequency is quantised to the FFT bin spacing (reported as
  `frequency_resolution_hz`); no THD/SNR yet. Input must be uniformly sampled (no resampling).
- **Import:** no Excel, HDF5, NPZ or vendor-specific binary formats. Quoted CSV fields may not
  span lines. Time-of-day-only timestamps (`10:15:02`) are not parsed. WAV amplitudes are not
  calibrated to volts.
- **UI:** command line and HTML reports only; no desktop/web UI.
- Records store the input's path and SHA-256 but do not copy the input file into the run folder.

## Development

```bash
pytest -q
```

Regenerate the synthetic example data after changing its models. `--force` overwrites the
files; the tests check that the committed files match the generator:

```bash
python scripts/generate_examples.py --force
```

CI (`.github/workflows/ci.yml`) runs the tests and the quick-start example on Ubuntu and Windows
with Python 3.11 and 3.13.
